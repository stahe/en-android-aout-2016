    2. Skeleton of an Android client communicating with a web service / jSON

    We now provide a skeleton Android application that communicates with one or more web services / jSON. This is the [client-android-skel] project, which can be found in the [architecture] folder of the examples:

    Studying this skeleton application will provide an opportunity to review certain points we encountered in the previous examples. This application will serve as a skeleton for all future applications. It was built after numerous iterations. It aims to factor as many elements as possible from the applications we will soon build into abstract classes to avoid having to write the same type of code over and over again, differing only in details. Its features are as follows:

    • asynchronous communication with the web server / jSON is handled using the RxJava library;
    • the lifecycle of a fragment (update, save, restore) is managed by its parent class [AbstractFragment], which calls certain methods of its child classes at specific times. The child class thus does not have to concern itself with the stages of the lifecycle but only with implementing certain methods required by its parent class;
    • the activity’s lifecycle (save / restore) is managed by an abstract class [AbstractActivity], which also requires the child activity to implement certain methods;
    • The class [AbstractActivity] is capable of managing an application with or without tabs, with or without a loading image, and with or without basic authentication against the web server / jSON. The presence or absence of these elements is determined by configuration;

    This skeleton was used for all subsequent examples. Due to their diversity, what worked for one example might not work for the next. Since the skeleton was used for a total of seven examples, numerous iterations took place. If it were used for an eighth example, it is possible that the specific nature of this new example would again generate new errors. Nevertheless, using this template will significantly simplify the writing of future examples. Indeed, managing a fragment’s lifecycle (update, save, restore) combined with the concept of fragment adjacency is particularly complex. Here, it is completely hidden within the [AbstractFragment] class.

    2.1. Android Client Architecture

    The proposed Android client is based on the following architecture:

    • the [DAO] layer implements the [IDao] interface. It is this layer that communicates with the web server / jSON;
    • there is only one activity that also implements the [IDao] interface. The views call upon it to access the server;
    • The views are implemented by fragments;

    The Android project reflects this architecture:

However, some of these operations may again trigger an implicit [select] software operation on one of the tabs. This selection does not necessarily result in a navigation to the associated fragment;

  private void showFragment(int i) {
    if (i < FRAGMENTS_COUNT && mViewPager.getCurrentItem() != i) {
      // no navigation on software tab selection
      session.setNavigationOnTabSelectionNeeded(false);
      // we recreate the two tabs for a title font issue
      tabLayout.removeAllTabs();
      tabLayout.addTab(tabLayout.newTab().setText("Vue1"), false);
      tabLayout.addTab(tabLayout.newTab().setText(String.format("Fragment n° %s", (i + 1))), false);
      // the fragment number to be displayed is set in session
      session.setNumFragment(i);
      // tab 2 is selected with navigation
      session.setNavigationOnTabSelectionNeeded(true);
      tabLayout.getTabAt(1).select();
    }
  }

    2.9. Conclusion

    At the end of this chapter, we have a [client-android-skel] Android client template project communicating with a web service / jSON with the following characteristics:

    • asynchronous communication with the web server / jSON is handled using the RxJava library;
    • the lifecycle of a fragment (update, save, restore) is managed by its parent class [AbstractFragment], which calls certain methods of its child classes at specific times. The child fragment thus does not have to concern itself with the stages of the lifecycle but only with implementing certain methods required by its parent class;
    • the activity’s lifecycle (save / restore) is managed by an abstract class [AbstractActivity], which also requires the child activity to implement certain methods;
    • The [AbstractActivity] class is capable of managing an application with or without tabs, with or without a loading image, and with or without basic authentication against the web server / jSON. The presence or absence of these elements is determined by configuration;
